1. Deep links return HTTP 404 even though the page renders correctly

Low frontend / hosting

What is wrong

The frontend is served from Azure Blob Storage static website hosting, with `index.html` set as both the index and the error document. A request for a client-side route such as /organiser/schools therefore returns the app correctly, but with a 404 status rather than 200.

Why it matters

Nothing user-facing breaks: the page loads, React Router resolves the path, and navigation works. The cost is that automated tooling sees a 404 — crawlers, uptime monitors and anything asserting on status codes. For a portal behind a login this is close to harmless, which is why it was accepted, but it should be a recorded decision rather than a surprise someone finds in devtools during a demo.

Where to look

  • Azure Storage account olympiadportalfe, $web container, error document set to index.html
  • docs/system-design.md — deployment section explains the trade-off

How to confirm it

curl -o /dev/null -w '%{http_code}' https://olympiadportalfe.z1.web.core.windows.net/organiser/schools returns 404 while the body is the app shell.

Suggested fix

Accept it, or put Azure Front Door in front of the storage account to rewrite unmatched paths with a 200. Front Door costs money, so this is only worth doing if a custom domain is wanted anyway. Azure Static Web Apps would solve it natively but is unavailable — its five regions do not intersect the five this subscription's policy permits.

Done when

  • Either the status is corrected, or the trade-off is recorded as an accepted decision

2. Values in .env are wrapped in quotes and break when copied elsewhere

Low config / developer experience

What is wrong

Every value in `backend/.env` and `frontend/.env` is wrapped in double quotes. Prisma and Vite both strip quotes when parsing a .env file, so local development works correctly and the problem is invisible day to day. But a value copied by hand into a Gitea secret or an Azure App Service setting carries the quotes with it, and the consuming code receives them as part of the string.

Why it matters

The resulting failures are confusing out of proportion to the cause. A quoted DATABASE_URL produces a connection error naming a host that does not exist, because the leading quote becomes part of the parsed URL. A quoted Supabase key simply fails to authenticate with no useful message. Someone hit this while configuring the Azure App Service; the values there were stripped before being set, which is why the deployed backend works.

Where to look

  • backend/.env and frontend/.env — all values quoted
  • backend/.env.example and frontend/.env.example — examples are unquoted, so the two disagree

How to confirm it

Copy a quoted value into any environment variable that is read directly from process.env rather than from a .env file, and observe the failure.

Suggested fix

Remove the quotes from the .env files so they match the examples, since nothing in them needs quoting. Add a line to the README warning that values must be pasted without quotes when configuring hosting or CI secrets.

Done when

  • The .env files and their examples use the same unquoted style
  • The README warns about hand-copying values

3. Two standing lint warnings, one of which can hide a real bug

Low frontend / code quality

What is wrong

`npm run lint` in frontend/ reports two warnings on every run. Both are pre-existing. The first is cosmetic; the second is the kind that can mask a genuine defect.

Why it matters

The unused catch parameter in Olympiads.tsx is harmless in itself, but it sits on a catch block that swallows the error entirely and sets an empty list, so a failed request is indistinguishable from an olympiad list that is genuinely empty. The exhaustive-deps warning in ExamSitting.tsx matters more: an effect that omits `started`, `handleSubmit` and `submitted` from its dependency array can close over stale values, and this is the exam auto-submit path — the place where a stale closure would be least acceptable. Warnings that are always present also train people to ignore lint output, which is how the next real one gets missed.

Where to look

  • frontend/src/pages/organiser/Olympiads.tsx line 29 — catch parameter 'err' is never used
  • frontend/src/pages/student/ExamSitting.tsx line 171 — useEffect missing 'started', 'handleSubmit', 'submitted'

How to confirm it

Run `npm run lint` in frontend/. Both warnings appear.

Suggested fix

In Olympiads.tsx, surface the error to the user instead of silently emptying the list. In ExamSitting.tsx, review the effect carefully before changing it — adding the dependencies naively may cause it to re-run more often than intended, so the fix is to restructure it rather than silence the warning.

Done when

  • npm run lint reports no warnings
  • A failed olympiad fetch shows an error rather than an empty list

4. Leftovers from the remark merge: an unused table, three tests that never run, and unused invitation emails

Low backend / cleanup

What is wrong

Three things were left behind when PR #53 brought in the result-linked remark_requests table. First, the table portal_remark_requests, which main used for remarks before, is no longer in the schema, but the migration that created it (20260924220100_intermediate_stories_data) still runs, so every database has it, unused. Second, backend/tests/intermediateStories.test.cjs uses Node’s built-in test runner, and neither Jest config nor CI runs it, so its three tests never run. Third, sendSchoolInviteEmail, sendStudentInviteEmail and sendEducatorInviteEmail in mailer.ts were revived with the email work, but invitations are in-app and nothing calls them.

Why it matters

None of it breaks anything today. But an unused table invites someone to write to it, which is how the old remark_requests table caused confusion before. Tests that never run give false confidence and quietly go stale. Unused senders make the mailer look like it sends invitations when it doesn’t.

Where to look

  • shared database: table portal_remark_requests (not in backend/prisma/schema.prisma)
  • backend/tests/intermediateStories.test.cjs (node:test; jest.config.js only runs tests/unit/**/*.test.js)
  • backend/src/lib/mailer.ts: the three invite senders, used only by tests/unit/lib/mailer.test.js

How to confirm it

grep -rn portal_remark_requests backend/src backend/prisma/schema.prisma finds nothing. node --test backend/tests/intermediateStories.test.cjs runs three tests that no CI log shows. grep -rn "InviteEmail" backend/src finds only the definitions.

Suggested fix

Check that portal_remark_requests is empty in the shared database, then add a migration that drops it with IF EXISTS. Move the three node:test cases into Jest under tests/unit if they cover something the Jest suites don’t, otherwise delete the file. Remove the invite senders and their tests, keeping deliver and sendNotificationEmail.

Done when

  • portal_remark_requests is gone from every database
  • Every backend test file is run by CI
  • mailer.ts exports only what the backend uses

What to do next

Ranked by how much they change the picture, not by effort:

  1. Wire up notification delivery. Done, 27 September. Delivery was already running on every lifecycle tick, but nothing tested it in CI. It now has tests against a real database, and they found one bug: a “results released” rule with an offset was scheduled before the results existed, so it never sent.   4. Correct the roadmap. Done, 27 September. Every status in docs/roadmap.md now matches this page (42 done, 7 in progress, 10 planned). I17 was missing from it entirely and has been added. Checking the last three unverified stories turned up one new problem: moderation (I7) can’t be used in the app, because the organiser both marks and moderates.
  5. Either honour olympiads.timezone or drop the column. Honoured, 27 September. Checking it turned up a real bug: both round forms stored the organiser’s typed time as if it were UTC, so in South Africa every round opened and closed 2 hours later than intended, and the dashboard’s table and edit form showed different times. The rounds already in the shared database were all closed, so no live schedule was affected; they simply now show their true times.
