1. Close remark_prisma_migrations without merging, and clear its leftovers from the shared database

Medium database / branches

What is wrong

The branch remark_prisma_migrations (one commit, 6e9e098, 24 September) adds remark requests and a table for de-duplicating notifications. Main has since built both differently: remark requests live in portal_remark_requests (the Prisma model remark_requests is mapped onto it), keyed by round and entrant, and notification delivery de-duplicates through portal_notifications. The branch's four migrations were applied to the shared database by hand, so the database still holds its tables, the old remark_requests (keyed by result_id) and sent_notifications, plus four migration records that main does not have, two of them both named add_remark_requests.

Why it matters

Merging the branch would put two conflicting definitions of remark_requests into schema.prisma, bring back the dropped invitations model, and replay migrations that main has replaced. The leftover tables are also a live trap: on 27 September, three remark requests were created and reviewed in the OLD remark_requests table (olympiads "Hunger games 2", "Essay competition" and "Multiple choice - How best can you cram"). Nothing on main reads that table, so organisers never see those requests. Main also rejects reasons shorter than 10 characters and one of these has 3, so they came from other code, most likely an unpushed branch pointed at the shared database. Whoever is building on it is building against a design main has replaced.

Where to look

  • branch remark_prisma_migrations, commit 6e9e098 (not merged into main)
  • shared database: tables remark_requests (3 rows) and sent_notifications (0 rows), enum type remark_status
  • shared database, _prisma_migrations: 20260923000000_add_remark_requests, 20260923100000_add_sent_notifications, 20260923125658_add_remark_requests, 20260923130303_remove_redundant_remark_relations
  • main: backend/src/routes/reviews.js, and model remark_requests with @@map("portal_remark_requests") in backend/prisma/schema.prisma
  • main's remark flow is covered by backend/tests/api/remarks.test.js

How to confirm it

git log origin/main..origin/remark_prisma_migrations shows the unmerged commit. On the shared database, SELECT migration_name FROM _prisma_migrations returns 16 rows against 11 migration folders on main, and SELECT count(*) FROM remark_requests returns 3 while portal_remark_requests is empty.

Suggested fix

First ask the team who created remark requests on 27 September, and point them at main's endpoints instead: POST /rounds/:id/remark and GET /rounds/:id/my-remark for students, GET and PATCH /rounds/:id/remarks for organisers. Then close the branch on Gitea without merging and delete it. Once nobody uses them, add a migration on main that drops remark_requests, the remark_status type and sent_notifications, using IF EXISTS so fresh databases (including CI's) still migrate cleanly. Finally, delete the four orphaned rows from _prisma_migrations so prisma migrate status is clean. Don't drop anything before the first step: the old table was written to on 27 September.

Done when

  • The person writing to the old remark_requests table has been found and moved to main's endpoints
  • The three existing rows are either moved to portal_remark_requests or confirmed to be test data
  • remark_prisma_migrations is closed without merging and deleted
  • A migration on main drops remark_requests, remark_status and sent_notifications if they exist
  • prisma migrate status against the shared database lists nothing that main does not have

2. One frontend integration test fails on Node 24

Medium frontend / tooling

What is wrong

On Node 24, `frontend/tests/integration/organiserManagement.test.tsx` fails the test 'creates the round, uploads its paper and returns to the dashboard'. Mock Service Worker throws during handler lookup for the multipart upload to `POST /rounds/:id/papers`, so the request never resolves, the redirect never happens, and the assertion on the path times out. The same test passes on Node 22.

Why it matters

The failure has nothing to do with the code being changed, so it costs whoever hits it real time before they work out it is environmental. CI pins Node 22 through actions/setup-node and is unaffected, but `backend/package.json` declares `"node": ">=22"`, which permits 24, and the frontend declares no engines field at all. So nothing warns a developer who installs a newer Node.

Where to look

  • frontend/tests/integration/organiserManagement.test.tsx — the failing test
  • backend/package.json line 29 — "node": ">=22"
  • frontend/package.json — no engines field

How to confirm it

Run `npm run test:integration` in frontend/ under Node 24, then under Node 22. 133 of 134 pass on 24; all 134 pass on 22.

Suggested fix

Cheapest correct fix is to pin the supported range so the mismatch cannot happen silently: set engines to `>=22 <23` in both packages, and add an engines field to the frontend. Separately, it is worth finding out whether MSW or undici is the actual cause, since Node 24 will eventually have to be supported.

Done when

  • Both packages declare a Node range that excludes 24
  • A developer on an unsupported Node gets a clear warning from npm

3. The e2e suite cannot run on the self-hosted runner

Medium ci / infrastructure

What is wrong

On the self-hosted CI runner (an Azure VM with 1 GiB of RAM) the Playwright suite takes 12 to 18 minutes and fails between one and four tests on timeouts, with around 718 MB of swap in use. The same suite completes in roughly 35 seconds on a developer machine. Chromium, the backend, the PGlite database and Vite are all resident at once, and the VM swaps heavily.

Why it matters

The failures are entirely environmental — the tests are correct and the machine is roughly 20 times too slow — but a deploy gate that fails for infrastructure reasons is worse than no gate, because the team learns to ignore it. The e2e job is currently pinned to the shared instance runners for this reason, which works but means e2e queues behind other teams' jobs at busy times.

Where to look

  • .gitea/workflows/ci.yml — the e2e job keeps runs-on: ubuntu-latest deliberately
  • frontend/playwright.config.ts — CI timeouts were raised to 180s per test and 30s per assertion
  • the runner advertises only prompt-engineers-azure, so e2e cannot land on it

How to confirm it

Temporarily add ubuntu-latest to the self-hosted runner's labels and re-run the suite. It will pick the job up and fail on timeouts.

Suggested fix

Leave e2e on the shared runners, which is the current arrangement and costs nothing. If queueing becomes a problem, the alternative is a larger VM — roughly four times the current cost — which is a budget decision rather than a technical one.

Done when

  • e2e passes consistently wherever it runs
  • The reason it does not run on our own runner is documented

5. Deep links return HTTP 404 even though the page renders correctly

Low frontend / hosting

What is wrong

The frontend is served from Azure Blob Storage static website hosting, with `index.html` set as both the index and the error document. A request for a client-side route such as /organiser/schools therefore returns the app correctly, but with a 404 status rather than 200.

Why it matters

Nothing user-facing breaks: the page loads, React Router resolves the path, and navigation works. The cost is that automated tooling sees a 404 — crawlers, uptime monitors and anything asserting on status codes. For a portal behind a login this is close to harmless, which is why it was accepted, but it should be a recorded decision rather than a surprise someone finds in devtools during a demo.

Where to look

  • Azure Storage account olympiadportalfe, $web container, error document set to index.html
  • docs/system-design.md — deployment section explains the trade-off

How to confirm it

curl -o /dev/null -w '%{http_code}' https://olympiadportalfe.z1.web.core.windows.net/organiser/schools returns 404 while the body is the app shell.

Suggested fix

Accept it, or put Azure Front Door in front of the storage account to rewrite unmatched paths with a 200. Front Door costs money, so this is only worth doing if a custom domain is wanted anyway. Azure Static Web Apps would solve it natively but is unavailable — its five regions do not intersect the five this subscription's policy permits.

Done when

  • Either the status is corrected, or the trade-off is recorded as an accepted decision

6. Values in .env are wrapped in quotes and break when copied elsewhere

Low config / developer experience

What is wrong

Every value in `backend/.env` and `frontend/.env` is wrapped in double quotes. Prisma and Vite both strip quotes when parsing a .env file, so local development works correctly and the problem is invisible day to day. But a value copied by hand into a Gitea secret or an Azure App Service setting carries the quotes with it, and the consuming code receives them as part of the string.

Why it matters

The resulting failures are confusing out of proportion to the cause. A quoted DATABASE_URL produces a connection error naming a host that does not exist, because the leading quote becomes part of the parsed URL. A quoted Supabase key simply fails to authenticate with no useful message. Someone hit this while configuring the Azure App Service; the values there were stripped before being set, which is why the deployed backend works.

Where to look

  • backend/.env and frontend/.env — all values quoted
  • backend/.env.example and frontend/.env.example — examples are unquoted, so the two disagree

How to confirm it

Copy a quoted value into any environment variable that is read directly from process.env rather than from a .env file, and observe the failure.

Suggested fix

Remove the quotes from the .env files so they match the examples, since nothing in them needs quoting. Add a line to the README warning that values must be pasted without quotes when configuring hosting or CI secrets.

Done when

  • The .env files and their examples use the same unquoted style
  • The README warns about hand-copying values

7. olympiads.timezone is stored but never read

Low backend / schema

What is wrong

The `olympiads` table has a `timezone` column defaulting to 'Africa/Johannesburg'. It is accepted when an olympiad is created and written to the database, and then never read again. Every time in the system is handled in UTC.

Why it matters

The column implies a capability that does not exist. Reading the schema, a developer would reasonably assume each olympiad's rounds open and close according to its own timezone, which is what user story A15 asks for. In practice they do not, and A2 (judge submissions against one authoritative clock) is only partly satisfied: the server clock is authoritative, but it is not timezone-aware per olympiad. Dead data that suggests a feature is worse than an absent column, because it hides the gap.

Where to look

  • backend/prisma/schema.prisma line 108 — timezone String @default("Africa/Johannesburg")
  • backend/src/services/olympiadService.js — writes it on create
  • nothing anywhere reads it

How to confirm it

Search the backend and frontend for `timezone`. Every hit is a write path or a validation rule; there is no read.

Suggested fix

Either honour it — convert round open and close times through the olympiad's timezone when evaluating and displaying them — or drop the column and treat everything as UTC explicitly. Both are defensible; leaving it as it is, is not.

Done when

  • Either round timing respects the olympiad timezone, or the column is removed
  • The decision is recorded in docs/system-design.md

8. Two standing lint warnings, one of which can hide a real bug

Low frontend / code quality

What is wrong

`npm run lint` in frontend/ reports two warnings on every run. Both are pre-existing. The first is cosmetic; the second is the kind that can mask a genuine defect.

Why it matters

The unused catch parameter in Olympiads.tsx is harmless in itself, but it sits on a catch block that swallows the error entirely and sets an empty list, so a failed request is indistinguishable from an olympiad list that is genuinely empty. The exhaustive-deps warning in ExamSitting.tsx matters more: an effect that omits `started`, `handleSubmit` and `submitted` from its dependency array can close over stale values, and this is the exam auto-submit path — the place where a stale closure would be least acceptable. Warnings that are always present also train people to ignore lint output, which is how the next real one gets missed.

Where to look

  • frontend/src/pages/organiser/Olympiads.tsx line 29 — catch parameter 'err' is never used
  • frontend/src/pages/student/ExamSitting.tsx line 171 — useEffect missing 'started', 'handleSubmit', 'submitted'

How to confirm it

Run `npm run lint` in frontend/. Both warnings appear.

Suggested fix

In Olympiads.tsx, surface the error to the user instead of silently emptying the list. In ExamSitting.tsx, review the effect carefully before changing it — adding the dependencies naively may cause it to re-run more often than intended, so the fix is to restructure it rather than silence the warning.

Done when

  • npm run lint reports no warnings
  • A failed olympiad fetch shows an error rather than an empty list
